# ADR-001 — Geography as Independent Domain Module

## Status

Accepted

## Context

Addresses contain geographic information, but address storage and geographic knowledge represent different responsibilities.

An address needs to store geographic identifiers such as country codes, administrative areas, cities, and postal codes.

However, interpreting these values requires external geographic knowledge:

- country metadata
- subdivision hierarchies
- geographic codes
- normalization rules
- postal rules

Embedding this knowledge inside the Address module would couple a generic address model to country-specific concepts and continuously expand its responsibility.

## Decision

Geography is implemented as an independent Core Module.

The Geography module owns geographic knowledge and provides contracts for resolving and interpreting geographic information.

The Address module remains responsible only for storing address data.

The dependency direction is:

```
@comity/geography
    ↓
@comity/primitives
```

Geography MUST NOT depend on:

- @comity/address
- @comity/customer
- order modules
- commerce-specific modules

## Responsibilities

@comity/geography owns:

- Country metadata
- Geographic subdivision concepts
- Geographic identifiers
- Normalization contracts
- Postal rule contracts

@comity/geography does NOT own:

- Address entities
- Address lifecycle
- Customer information
- Shipping logic
- Billing logic
- Tax calculation
- Order concepts

## Address Relationship

The relationship between Address and Geography is enrichment, not ownership.

Address stores geographic identifiers:

```
Address
 ├── countryCode
 ├── administrativeArea
 ├── city
 └── postalCode
```

Geography interprets and enriches these identifiers:

```
Address data
    ↓
Geography resolution
    ↓
Geographic metadata and rules
```

The Address module does not require geographic metadata to represent an address.

## Consequences

Positive consequences:

- Address remains a universal and infrastructure-independent model.
- Geographic logic can evolve independently.
- Country-specific rules do not leak into the Address module.
- Geographic data providers can be replaced without changing domain models.

Negative consequences:

- Consumers may need to compose Address and Geography when geographic interpretation is required.
- Geographic resolution becomes an explicit operation instead of an implicit Address behavior.

## Alternatives Considered

### Geography inside Address

Rejected.

This would make Address responsible for geographic knowledge and introduce country-specific behavior into a generic domain model.

### Country-specific Address subclasses

Rejected.

Examples:

- ItalianAddress
- USAddress
- GermanAddress

This approach does not scale and mixes geographic rules with address representation.

### Geography as an Adapter only

Rejected.

Geography defines domain concepts and contracts, not only integrations with external systems.
